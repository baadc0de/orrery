# References — Annotated Bibliography

This is the consolidated bibliography for the Orrery architecture doc set: every external source the design load-bears on, deduplicated and organized by topic, with one line each on why it matters. Entries cite the decision sections (Dn) of the ADR they support; sibling docs reference these same links inline.

Normative source: [DECISIONS.md](DECISIONS.md) — supports D1–D17; this file adds no decisions.

## QUIC & NAT traversal

- [iroh](https://github.com/n0-computer/iroh) — The chosen transport (D3): P2P QUIC dialed by ed25519 `NodeId`, hole punching coordinated through self-hostable relays, 1.0 wire-protocol stability guaranteed across 1.x.
- [iroh 1.0: dial keys, not IPs](https://pinggy.io/blog/iroh_1_0_dial_keys_not_ips/) — Source of the headline numbers behind D3: ~90% direct hole-punch success in production, ~95% of bytes on direct paths, 200M endpoints created in a 30-day window.
- [iroh FAQ](https://docs.iroh.computer/about/faq) — Documents relay self-hosting requirements (public IP + DNS + ACME TLS) and that n0's public relays are dev-only — why D3/D12 mandate a self-hosted ≥3-region fleet.
- [iroh on QUIC multipath](https://www.iroh.computer/blog/iroh-on-QUIC-multipath) — Why relay→direct migration is now a native QUIC multipath switch instead of a congestion-controller-resetting path swap; the basis of "connect instantly via relay, migrate later".
- [noq](https://github.com/n0-computer/noq) — iroh's standalone quinn-derived QUIC stack (RFC 9221 datagrams, multipath, QUIC Address Discovery, NAT-traversal draft); the documented hedge if iroh's identity layer ever chafes (D3).
- [draft-seemann-quic-nat-traversal](https://datatracker.ietf.org/doc/html/draft-seemann-quic-nat-traversal) — The IETF draft standardizing hole punching inside QUIC (ADD_ADDRESS/PUNCH_ME_NOW frames, ICE-like pairing) that noq implements; Orrery punches via a standard, not ad-hoc probing.
- [P2P QUIC (Marten Seemann)](https://seemann.io/posts/2024-10-26---p2p-quic/) — Design rationale for QUIC-native traversal and why the QUIC header demuxes cleanly next to STUN on one socket.
- [Tailscale: How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works) — The canonical traversal explainer; quantifies the hard cases (single hard NAT ~98% after ~20 s birthday-paradox probing; CGNAT↔CGNAT effectively never) that make the relay tail a product requirement.
- [Tailscale: NAT traversal improvements, pt. 1](https://tailscale.com/blog/nat-traversal-improvements-pt-1) — Independent corroboration of the >90% direct-connection ceiling, the start-on-relay-then-migrate UX Orrery adopts, and the failure-cause taxonomy (symmetric NAT, CGNAT, UDP-blocked) used to size the permanently-relayed tail (D3).
- [quinn](https://github.com/quinn-rs/quinn) — Community-standard Rust QUIC; the raw backend behind the `aeronet_io` hedge (LAN, dedicated server, tests) in D3; supports client+server on one UDP socket.
- [rust-libp2p](https://github.com/libp2p/rust-libp2p) — Rejected alternative (D3): ~70% measured punch success, 13-month release gap, framework overhead misfit for a latency-critical game loop.
- [Large-scale DCUtR measurement (arXiv 2510.27500)](https://arxiv.org/html/2510.27500v1) — The 70%±7.1% hole-punch success measurement that disqualified libp2p's DCUtR and set the bar iroh clears.
- [ant-quic](https://github.com/dirvine/ant-quic) — quinn derivative implementing the NAT-traversal draft directly; monitored as a punch-without-iroh option, not adopted (small community, no success-rate data).
- [s2n-quic](https://github.com/aws/s2n-quic) — Rejected for P2P (datagrams behind an unstable feature flag, no traversal story); remains reasonable for datacenter-internal RPC where traversal is irrelevant.
- [quiche](https://github.com/cloudflare/quiche) — Rejected for the P2P base: battle-tested and fast, but sans-IO with a bring-your-own event loop and no P2P affordances.

## Bevy netcode ecosystem

- [lightyear](https://github.com/cBournhonesque/lightyear) — The prediction/rollback, interpolation, delta-compression, and priority layer Orrery configures rather than rewrites (D4, D8); runs on replicon since 0.27.
- [lightyear book](https://cbournhonesque.github.io/lightyear/book/) — Concept documentation for the primitives `orrery_predict` configures: prediction sets, rollback, interpolation timelines, rooms.
- [lightyear releases](https://github.com/cBournhonesque/lightyear/releases) — The churn record (4 breaking releases in 10 months; authority handling "still in flux") behind D4's version-pinning and upstream-contribution posture and risk D17.1.
- [bevy_replicon](https://github.com/simgine/bevy_replicon) — The replication substrate (D4): registered-component diffs, per-client visibility (the cell-interest mechanism of D5), and the change-detection stream the persistence uplink consumes (D11).
- [aeronet](https://github.com/aecsocket/aeronet) — Bevy-native session/IO abstraction; `aeronet_io` is explicitly designed for third-party IO layers — the seam where iroh plugs in and where a quinn backend swaps in (D3, D4).
- [aeronet_iroh (in-repo prototype)](https://github.com/aecsocket/aeronet/tree/main/crates/aeronet_iroh) — Unpublished iroh IO layer in the aeronet repo; `orrery_aeronet_iroh` mirrors it and is the upstream candidate (D4, D15).
- [aeronet_replicon](https://crates.io/crates/aeronet_replicon) — The aeronet→replicon bridge; one IO-layer implementation serves both lightyear and raw replicon through it.
- [ggrs](https://github.com/gschup/ggrs) / [bevy_ggrs](https://github.com/gschup/bevy_ggrs) — The most battle-tested Bevy P2P rollback stack; rejected as the world model (deterministic lockstep, D2) but its snapshot/rollback-schedule design is a reference for rollback mechanics.
- [naia](https://github.com/naia-lib/naia) — Rejected (UDP/WebRTC only, trails Bevy) but the closest existing precedent for per-entity authority delegation to clients (D4, D7).
- [bevy_quinnet](https://github.com/Henauxg/bevy_quinnet) — Focused quinn-based client-server QUIC for Bevy; explicitly no P2P — evidence that nothing in the ecosystem did hole punching before Orrery (D4).
- [matchbox](https://github.com/johanhelsing/matchbox) — WebRTC full-mesh P2P with signaling-server ICE; the browser-parity contingency (add a matchbox IO backend if WASM ever matters) rather than the primary stack (D3, R9).
- [Rock and Rollback (metabrew)](https://www.metabrew.com/article/rock-and-rollback-realtime-multiplayer-games-with-bevy) — Demonstrates state-based physics rollback in Bevy without determinism — validates D8/D13's snap-and-reconcile posture.
- [avian3d](https://crates.io/crates/avian3d) — The presentation/gameplay physics engine (D13), chosen for Bevy-nativeness and lightyear integration.
- [avian determinism notes](https://deepwiki.com/avianphysics/avian/10.3-determinism) — libm routing is a mitigation, `parallel` breaks even local determinism, cross-platform "requires more testing" — why D9 scopes determinism to a verifiable core instead of trusting the physics engine.
- [rapier determinism guide](https://rapier.rs/docs/user_guides/rust/determinism/) — enhanced-determinism is mutually exclusive with SIMD/parallel features; the documented-alternative physics engine's own evidence for D2's rejection of lockstep.

## Netcode theory & industry practice

- [Gambetta: Client-side prediction and server reconciliation](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html) — The sequence-numbered input reconciliation algorithm D8 applies per entity rather than globally.
- [Source Multiplayer Networking (Valve)](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking) — Origin of the 100 ms entity-interpolation buffer (cl_interp) and rewind-based lag compensation; the reference for D8's interpolation and hit-rewind numbers.
- [Overwatch Gameplay Architecture and Netcode (GDC 2017)](https://www.gdcvault.com/play/1024001/-Overwatch-Gameplay-Architecture-and) — Industrial predict-everything on ECS command frames; source of the ~220 ms hit-prediction cutoff precedent (D8) and the "rollback needs a trusted authority" framing D2 answers.
- [Overwatch netcode deep dive (Edgegap)](https://edgegap.com/blog/game-backend-deep-dive-overwatch-2016-netcode-architecture-rollback) — Accessible numeric summary of the GDC talk (command-frame timing, client lead, time dilation) used throughout D8.
- [SnapNet: Netcode architectures pt. 2 — Rollback](https://www.snapnet.dev/blog/netcode-architectures-part-2-rollback/) — The resimulation-budget arithmetic (60 Hz absorbing 300 ms leaves ~1.1 ms/frame) and spiral-of-death failure mode that structurally disqualify whole-world rollback (D2, D8).
- [Gaffer: Networked Physics in VR](https://gafferongames.com/post/networked_physics_in_virtual_reality/) — The weak-authority/strong-ownership dual-sequence-number scheme with host confirmation that D7 adopts nearly verbatim; proved 4-player shared physics under 1 Mbps on non-deterministic PhysX.
- [Gaffer: Snapshot Compression](https://gafferongames.com/post/snapshot_compression/) — Quantize + delta-against-acked-baseline + priority accumulation (17.37 Mbps → ~256 kbps); the lineage of D8's bandwidth pipeline.
- [Gaffer: State Synchronization](https://gafferongames.com/post/state_synchronization/) — The foundational argument that state sync does not require determinism — the theoretical basis of D2.
- [Gaffer: Deterministic Lockstep](https://gafferongames.com/post/deterministic_lockstep/) — The requirements (perfect determinism, identical full state) whose impossibility at Orrery's scale drives D2's rejection.
- [Photon Fusion: Shared Mode / master client](https://doc.photonengine.com/fusion/current/manual/shared-mode-master-client) — The single-State-Authority-per-object invariant D7 adopts; also documents that Fusion disables prediction/rollback/lag-compensation in this mode (eventual consistency only) — exactly the gap Orrery closes.
- [Unity NGO: distributed authority](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.11/manual/terms-concepts/distributed-authority.html) — Ownership permissions and automatic redistribution on disconnect (the orphan-reassignment precedent in D7); its own "not reliable where instances may cheat" admission motivates the witnessing layer (D10).
- [Photon Quantum: fixed-point math](https://doc.photonengine.com/quantum/current/manual/quantum-ecs/fixed-point) — Commercial proof that cross-platform deterministic rollback requires abandoning IEEE floats (Q48.16); why D9 uses integer math for discrete outcomes and tolerance bands for continuous state.
- [High Level Architecture (IEEE 1516)](https://en.wikipedia.org/wiki/High_Level_Architecture) — The standards-body ownership-management precedent (negotiated vs. unconditional divestiture) behind D7's cooperative vs. crash handoff split.
- [Croquet](https://github.com/croquet/croquet) — Synchronized-computation-via-reflectors architecture; rejected (latency floor, monolithic VM) but its cheap stateless-relay idea survives in the relay/coordinator tier (D2, D12).

## P2P topology & shipped precedent

- [Donnybrook (SIGCOMM 2008)](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/donnybrook.pdf) — The empirical mesh ceiling (~12·n kb/s receive, 16–32 interacting players) and the interest-set + low-rate-doppelganger pattern behind D6's regimes and the 24-entity high-rate set.
- [P2P MMOG survey (ACM Computing Surveys 46(1))](https://dl.acm.org/doi/10.1145/2522968.2522977) — The six jointly-unsolved problems (interest management, dissemination, NPC hosting, persistence, cheating, incentives) that killed academic P2P MMOs; Orrery addresses each in turn — NPC hosting, historically the weakest answer, via [04-authority.md](04-authority.md)'s active-entity assignment policy (registrar-granted weak authority to the nearest subscribed peer with headroom, per-peer load caps) plus field-host promotion where trusted NPC simulation is required.
- [VON: Voronoi overlay network](https://scispace.com/pdf/von-a-scalable-peer-to-peer-network-for-virtual-environments-34llq742sv.pdf) — The academically elegant Voronoi AOI overlay; rejected in D5 (never shipped, fragile under churn/adversaries, no storage story).
- [VAST spatial pub/sub (ACM MMSys 2023)](https://dl.acm.org/doi/10.1145/3587819.3592554) — The surviving research lineage of decentralized spatial pub/sub; tracked, not adopted.
- [Elite Dangerous networking (lavewiki)](https://www.lavewiki.com/network) — The shipped-precedent core of D6/D12: central servers instruct nearby players to form P2P islands while central services own persistent state.
- [Elite Dangerous systems architecture (Frontier forums)](https://forums.frontier.co.uk/threads/elite-dangerous-systems-architecture.43546/) — First-party description of the `edServer` instancing/matchmaking role that `orrery_coordinator` reprises.
- [Destiny architecture notes (nessus42 gist)](https://gist.github.com/nessus42/df399f31e4ab41192cbd51b32e9d7b73) — Destiny 1's player-hosted physics hosts + datacenter persistence ("no peer-to-peer interference" for durable character data) — the durable-truth boundary D11 enforces.
- [How Destiny 2 uses both P2P and authoritative servers (Edgegap)](https://edgegap.com/blog/multiplayer-game-hosting-deep-dive-exploring-how-destiny-2-uses-both-peer-to-peer-authoritative-servers) — Destiny 2 moved hosts into datacenters specifically to kill host migration; the precedent for infrastructure field hosts (D6).
- [For Honor moves to dedicated servers (Ubisoft)](https://www.ubisoft.com/en-us/game/for-honor/news-updates/2HayRoZjbJzSEJAhJMpeF7/for-honor-now-on-dedicated-servers-on-all-platforms) — The most explicit shipped retreat from elected-host P2P (migration, resyncs, NAT, match completion) — why D6 bans player hosts.
- [Host migration in P2P games (Edgegap)](https://edgegap.com/blog/host-migration-in-peer-to-peer-or-relay-based-multiplayer-games) — Failure-mode taxonomy of host migration; background for D6's "field host is infrastructure, never a player" rule.
- [Diablo II multiplayer FAQ (Battle.net)](https://classic.battle.net/diablo2exp/faq/multiplayer.shtml) — Open vs. closed realms: the canonical demonstration that server-side storage + validation is the effective anti-duping control (D10, D11).
- [Diablo II hacking retrospective (amtal gist)](https://gist.github.com/amtal/bf941bde443eefc7d4626fd439d7f480) — Mechanism-level detail of client-trusted-state exploitation; threat-model input for D10.
- [GTA Online money-wipe enforcement](https://www.sportskeeda.com/gta/gta-online-money-generators-illegal-will-get-account-wiped-reset) — A decade of P2P cheating corrected after the fact — the cautionary tale for validating too late that motivates pre-commit intent validation (D10, D11).
- [Steam Datagram Relay](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay) — Valve's production relay fleet: IP privacy, DoS protection, backbone routing sometimes beating BGP — design prior art for the self-hosted relay tier (D3, D12).

## Persistence & storage engines

- [FoundationDB performance](https://apple.github.io/foundationdb/performance.html) — The numbers D11 budgets against: 0.1–1 ms reads, 1.5–2.5 ms commits at <75% load, linear scaling to 8.2 M ops/s on 384 processes.
- [FoundationDB known limitations](https://apple.github.io/foundationdb/known-limitations.html) — The 5 s transaction / 10 KB key / 100 KB value / 10 MB transaction constraints that shape the checkpoint pattern and terrain-chunk sharding (D11).
- [FoundationDB SIGMOD paper](https://www.foundationdb.org/files/fdb-paper.pdf) — Architecture and the multi-DC tail-latency data (~22 ms mean, 281 ms p99.9 with satellites) behind keeping each game cluster single-region.
- [foundationdb-rs](https://github.com/foundationdb-rs/foundationdb-rs) — The mature Rust binding (0.11, BindingTester run hourly against thousands of seeds) that makes FDB adoptable from a Rust-only team (D11, D14).
- [fdb-kubernetes-operator](https://github.com/foundationdb/fdb-kubernetes-operator) — The manageable-ops path for 3–5 node clusters cited in D11; mitigation for risk D17.4.
- [FDB issue #11510 (hotspot pre-splitting)](https://github.com/apple/foundationdb/issues/11510) — The continuous-keyspace write-hotspot failure mode a crowd event would trigger under range sharding; named risk D17.4 and input to hotspot-splitting design (D11).
- [Copy-on-update checkpointing for MMOs (Cornell, VLDB 2009)](https://www.cs.cornell.edu/~tuancao/2009-VLDB-Checkpoint.pdf) — The MMO checkpoint-recovery research behind cell actors' 20 s jittered copy-on-update checkpoints (D11).
- [Netherite (arXiv 2103.00033)](https://arxiv.org/pdf/2103.00033) — The commit-log + periodic-checkpoint + replay-for-recovery pattern the journal design follows (D11).
- [ScyllaDB petabyte-scale benchmark](https://thenewstack.io/what-we-learned-benchmarking-petabyte-scale-workloads-with-scylladb/) — p99 writes <7 ms at 7 M TPS: why Scylla is the documented runner-up if sustained write volume outgrows FDB (D11).
- [ScyllaDB LWT guidance](https://www.scylladb.com/2020/07/15/getting-the-most-out-of-lightweight-transactions-in-scylla/) — Paxos LWTs are 3–4× slower, single-partition, and collapse under contention — why Scylla lost the trade-safety comparison to FDB's serializable transactions (D11).
- [fjall 3](https://fjall-rs.github.io/post/fjall-3/) — Active pure-Rust LSM (~42 K LOC vs RocksDB's ~700 K); the local engine choice for journal/staging (D11, D14).
- [redb](https://crates.io/crates/redb) — Stable, boring pure-Rust ACID B-tree; the alternative local engine if LSM write-amp isn't needed.
- [openraft](https://github.com/databendlabs/openraft) — Pre-1.0, incomplete chaos testing: the concrete reason D11 refuses to build a general replicated store and keeps the custom layer thin and single-purpose.
- [FDB's simulator-first lesson (jbaker.io)](https://jbaker.io/2022/05/09/project-loom-for-distributed-systems/) — FoundationDB built a deterministic simulator before the database; the canonical argument that testing, not implementation, is the cost of rolling your own distributed store.
- [Redis persistence semantics](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) — Async replication loses acknowledged writes on failover; AOF everysec loses up to 1 s — why no in-memory store is Orrery's system of record (D11).
- [SpacetimeDB](https://spacetimedb.com/) — The database-as-game-server wildcard (powers BitCraft); validates the domain but replaces the Bevy + P2P architecture rather than persisting under it — reviewed, not adopted.

## Spatial partitioning & interest management

- [big_space](https://github.com/aevyrie/big_space) — The canonical cell coordinate (D5): nestable integer `GridCell` + local `f32` transform solves float precision at huge coordinates and already ships grid-cell spatial hashing; tracked risk: needs a Bevy 0.19 port (D17).
- [S2 cell hierarchy](https://s2geometry.io/devguide/s2cell_hierarchy.html) — The 64-bit cell-ID bit layout `CellId` copies (Hilbert/Morton position bits, sentinel bit, parent = key prefix, sorted order = spatial locality) — copied without the spherical geodesy (D5).
- [lindel](https://lib.rs/crates/lindel) — Morton + Hilbert linearization crate; Morton for the runtime/network ID, optional Hilbert at the storage layer if scan locality measurably matters (D5).
- [kiddo](https://crates.io/crates/kiddo) — Actively maintained k-d tree for per-cell in-memory nearest-neighbor queries (D5, D14); used instead of the stalled bevy_spatial.
- [Unreal Replication Graph](https://www.unrealengine.com/en-US/tech-blog/replication-graph-overview-and-proper-replication-methods) — Grid-cell interest lists serving 100-player/50 k-actor Fortnite matches; the shipped precedent for cell-based replication groups and the 27-cell AOI (D5).
- [TiKV data sharding](https://tikv.org/deep-dive/scalability/data-sharding/) — The range-shard-not-hash rationale (prefix aggregation, metadata-only split/merge) behind the `[cell_id][entity_id]` keyspace (D5, D11).
- [Minecraft region file format](https://minecraft.wiki/w/Region_file_format) — Chunk-keyed storage with empty-section elision: the enduring sparse-world persistence precedent for terrain chunks (D11).
- [Second Life region crossing](https://wiki.secondlife.com/wiki/Region_crossing) — Twenty years of timing-sensitive hard-boundary handoff failures; the negative precedent behind handoff hysteresis and keep-holder-across-cells (D5, D7).
- [EVE's 14,274-ship battle (VentureBeat)](https://venturebeat.com/2019/03/25/why-ccp-games-crammed-14274-spaceships-into-an-eve-online-battle) — The static region-per-server ceiling (one solar system = one single-threaded node, time dilation); why cells, not regions, are Orrery's unit (D5, D6).
- [EVE Aether Wars (CCP × Hadean)](https://www.ccpgames.com/news/2019/ccp-games-and-hadean-to-showcase-the-next-eve-aether-wars-in-november) — 14 k-client octree-partitioned demo whose vendor then pivoted away from gaming — evidence that adaptive octrees as the partition unit lack shipped survivors (D5).
- [Star Citizen Replication Layer](https://starcitizen.tools/Replication_layer) — Live validation of the key split Orrery makes: entity state owned by a persistence/replication layer independent of simulation authority (D5, D11).
- [Star Citizen server meshing at CitizenCon 2025](https://hangarbase.org/news/star-citizen-the-expanded-server-mesh-the-future-of-the-verse-revealed-at-citizencon-2025) — Dynamic authority split/merge by player density in production; precedent for hotspot cell splitting and field-host promotion (D6, D11).
- [Improbable handover patent US10878146](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10878146) — SpatialOS's authority-overlap/handoff technique (entities stay with their current worker inside overlap zones) — the anti-thrash hysteresis lesson D5 adopts, and IP to be aware of.
- [Worlds Adrift shutdown (Game Developer)](https://www.gamedeveloper.com/business/bossa-shutting-down-i-worlds-adrift-i-says-game-is-no-longer-commercially-viable-) — The SpatialOS cautionary tale: transparent fine-grained distribution was operationally expensive and fatally coupled the game to proprietary infrastructure.
- [Interest management survey (ACM Computing Surveys 46(4))](https://dl.acm.org/doi/10.1145/2535417) — The field map from aura-nimbus (Benford & Fahlén) onward; grounds the cell-subscribe-then-filter two-stage AOI design (D5).
- [Voronoi State Management for P2P MMOGs](https://www.researchgate.net/publication/224305544_Voronoi_State_Management_for_Peer-to-Peer_Massively_Multiplayer_Online_Games) — The strongest Voronoi-partition proposal for P2P state; rejected with VON/VAST (unstable under churn, no storage key story) in D5.
